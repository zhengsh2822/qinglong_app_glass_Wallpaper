Vibe Coding 设计规范

1. 设计风格与视觉规范
1.1 主色调选择原则
Vibe Coding 的视觉核心在于“克制”与“沉浸”。主色调的选择应遵循低饱和度原则，避免使用高纯度、高对比度的荧光色。推荐采用莫兰迪色系或带有灰阶的柔和色彩，以降低视觉疲劳，营造高级感与舒适感。

1.2 色彩系统定义
为确保全局视觉的一致性，色彩系统需严格划分为以下三类：

色彩类型: #00cccc (品牌色)
定义与用途: 品牌色及核心交互色
规范说明: 用于主要按钮、关键链接、激活状态，需保持低饱和度

--------------------------------------------------

色彩类型: 辅助色
定义与用途: 补充与强调色
规范说明: 用于次要操作、标签、进度条，饱和度应略低于主色

--------------------------------------------------

色彩类型: 中性色
定义与用途: 文本、背景、边框
规范说明: 采用不同灰阶，用于构建页面骨架与信息层级

1.3 字体规范
中英文字体配对：优先使用系统原生字体以保证渲染性能与跨平台一致性。推荐组合："PingFang SC", "Helvetica Neue", Arial, sans-serif。
间距系统：全局采用 8px 基准网格。所有内外边距必须是 8 的倍数（如 8px, 16px, 24px, 32px），以保证视觉节奏的韵律感。

1.4 圆角与阴影层级
圆角规范：统一使用 12px 作为标准组件圆角，大型卡片或弹窗可使用 16px 或 18px，避免使用全圆角（除非是胶囊按钮）。
阴影层级：严格限制阴影层级，最多不超过 3 级，以体现克制感：
  - Level 1 (微阴影): 0 2px 8px rgba(0, 0, 0, 0.04)，用于卡片悬浮。
  - Level 2 (中阴影): 0 4px 16px rgba(0, 0, 0, 0.08)，用于下拉菜单。
  - Level 3 (强阴影): 0 8px 24px rgba(0, 0, 0, 0.12)，仅用于模态弹窗。

2. UI 组件库选型规范
2.1 推荐组件库与选型理由
本项目统一采用 uni-ui 或 uview-plus（适配 Vue3）。
选型理由：两者均深度适配 Vue3 组合式 API，具备完善的 TypeScript 支持；内置丰富的业务组件，能够大幅减少自定义样式的编写，契合 Vibe Coding 快速构建、注重体验的理念。

2.2 组件库主题定制与禁止事项
主题定制方法：严禁在业务代码中直接覆盖组件库的默认 CSS。必须通过组件库提供的 SCSS 变量文件或配置项进行全局主题注入。
禁止混用：项目中绝对禁止同时引入多个 UI 组件库（如同时使用 uni-ui 和 uview-

2.3适配安卓状态栏和小白条透明背景（沉浸效果）
最好一次适配小米、vivo、Oppo、荣耀设备

3. 项目架构规范
3.1 标准文件目录结构
项目需遵循以下标准化目录结构，确保职责清晰：
src/
├── components/     # 全局通用组件
├── pages/          # 页面视图，按业务模块划分文件夹
├── composables/    # Vue3 组合式函数
├── store/          # 状态管理模块
├── styles/         # 全局样式与 Token 变量
├── utils/          # 纯工具函数
└── static/         # 静态资源

3.2 模块划分与复用封装
模块划分原则：按业务领域而非技术类型划分页面与路由。
复用模块封装：当同一逻辑或 UI 片段在 3 个及以上页面使用时，必须抽取为独立组件或 Composable。组件命名遵循 PascalCase，Composable 必须以 use 前缀命名。

3.3 路由与状态管理
路由组织：采用扁平化路由配置，通过 meta 字段控制页面权限、缓存策略及过渡动画。
状态管理方案：推荐使用 Pinia。按业务模块拆分 Store，避免单一巨型 Store；状态命名需具备明确的业务语义。

4. 设计 Token 管理体系
4.1 Token 分类与命名规范
设计 Token 是连接设计与开发的桥梁，必须采用语义化命名，禁止使用具象颜色名（如 $blue-500）。

Token 类别: 颜色
命名规范示例: --color-primary-base
说明: 基础主色

Token 类别: 字体
命名规范示例: --font-size-body-lg
说明: 正文大字号

Token 类别: 间距
命名规范示例: --space-md
说明: 中等间距 (16px)

Token 类别: 圆角
命名规范示例: --radius-card
说明: 卡片圆角

Token 类别: 阴影
命名规范示例: --shadow-level-1
说明: 一级阴影

4.2 集中管理与组件库打通
集中管理：所有 Token 必须统一定义在 src/styles/tokens.scss 中，通过 CSS Variables 或 SCSS 变量导出。
打通方法：将 Token 变量映射至 uni-ui / uview-plus 的主题配置文件中，实现“修改 Token 即全局生效”。

4.3 Token 使用示例
// 错误示范：直接使用硬编码颜色
.btn { background-color: #5b8c85; padding: 16px; }

// 正确示范：使用语义化 Token
.btn {
  background-color: var(--color-primary-base);
  padding: var(--space-md);
}

5. 自查清单
5.1 开发前自查项
- 是否已明确该页面的业务目标与核心交互流程？
- 所需组件是否已在现有组件库中存在？避免重复造轮子。
- 页面所需的颜色、间距是否已有对应的 Token 定义？

5.2 开发后自查项
- 页面是否严格遵循 8px 基准网格，无奇数像素间距？
- 是否存在硬编码的颜色值或字号？
- 新增的样式是否破坏了全局主题的一致性？

5.3 代码审查要点
规范合规性：审查代码是否混用了多个组件库，是否违背了 Token 体系。
架构合理性：审查 Composable 的拆分是否合理，Store 是否存在状态冗余。
视觉还原度：结合设计稿，审查低饱和度、克制配色的视觉风格是否准确落地。

6. 竞品参考原则
6.1 只学习布局思路
在调研竞品时，重点分析其信息架构、交互逻辑与页面布局策略。学习其如何通过留白、卡片嵌套来引导用户视线，而非关注其表面的视觉装饰。

6.2 禁止直接复制样式
严禁使用浏览器开发者工具直接复制竞品的 CSS 代码或颜色值。竞品的样式可能包含历史包袱或与其品牌强绑定的特定设计，直接复制极易导致项目视觉风格失控。

6.3 优先使用已定规范
当遇到竞品中优秀的交互细节但本项目规范未覆盖时，应首先评估是否将其抽象为通用规范。在规范未更新前，必须优先使用当前已定义的 Vibe Coding 规范，确保产品体验的连贯性。
